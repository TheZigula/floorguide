## Step 2 - backend/ingest.py, two Chroma collections - 12:48
backend/ingest.py chunks data/corpus and data/assets into ./chroma and writes BOTH collections: corpus_local (Chroma default MiniLM, 384-dim, no key) and corpus_openai (text-embedding-3-small, key read from .env by Chroma itself, never in code). Local is written first so the no-key fallback index is always populated even if the OpenAI path is down; a failure in one collection is caught and reported, never fatal to the other. Run: 16 documents + 3 asset records -> 35 chunks, both collections count=35, vector_backend=openai, 5.3 s.
Chunking is heading-aware, 1400 chars max with 150 overlap, and the number is derived not guessed: I measured every heading-led section in the corpus and the largest is 1,149 chars (SP-01's lockout steps; MM-P102 Sec 4.2 is 1,094), so a 1,400 budget keeps EVERY section whole in one chunk with its own heading and a service-table row is never separated from the label above it. Overlap only triggers on a section longer than the budget and carries the tail forward at a word boundary. Every chunk carries source_id, title, category, authority, stale, revised, source_path, chunk_index, content_sha.
Idempotent, verified by running it twice: ids are "<path relative to repo root>::<chunk index>" and each row stores a sha256 of its text, so the second run printed written=0 skipped=35 per collection with count still 35, in 1.7 s and zero embedding tokens. A chunk whose source text changed is re-embedded; a chunk that no longer exists in the source is deleted, so a stale row cannot linger in the index and be retrieved. Per the pilot's addendum, ensure_ingested(corpus_dir, persist_dir) -> dict is importable and does NOTHING at import time; __main__ just calls it; the returned dict carries documents_read, asset_records_read, chunks_total, chunks_written, chunks_skipped, per-collection written/skipped/deleted/count/status/embedder, instruction_shaped_chunks, vector_backend, ready. Relative paths resolve against the repo root, not the CWD, so it works from a server started anywhere.

## Step 4 - eval/run_eval.py and eval/thresholds.json, fail-closed - 12:59
run_eval.py calls the live backend once per case on its own thread id, code-grades the five gate cases, judge-scores the other five, writes eval/results.json, and prints the transcript line. Fail-closed by construction: exit 1 on an empty golden set, on scored != attempted (a case that could not be scored never looks like a pass), on any code-graded case failing, and on the must-fail control NOT failing. Thresholds live in eval/thresholds.json, are read at runtime, were set before the first scored run, and are copied into results.json with every run so a reader sees what was in force.
Ragas 0.4.3 modern path, verified live against the API before the runner was written: evaluate() rejects these metrics, so each row is scored with await metric.ascore(...). I found a real trap the note in CLAUDE.md does not mention - the three metrics take DIFFERENT arguments (AnswerRelevancy.ascore takes no retrieved_contexts, ContextPrecisionWithReference.ascore takes no response), so a uniform kwargs bag raises TypeError. The accepted names are declared per metric and filtered. The legacy path (ragas.metrics + LangchainLLMWrapper + evaluate(raise_exceptions=True)) is kept as a real fallback and stdout says which path ran.
What the judge is shown is measured, not assumed. A correct, well-cited answer scored 0.5 on faithfulness against one thin sentence of context in my probe, exactly the failure the brief warns about, so the runner rebuilds the FULL chunk behind each cited source out of the same Chroma collection the backend searched (matched by source id and by the snippet text), minus the stale and injected sources. The API's snippet is an abbreviation for the UI; the model saw the whole chunk. If the index cannot be opened it falls back to snippets and the row says so, because a quiet substitution would make the scores unreadable.
Pacing and cost: a sliding 60-second window holds estimated judge tokens under the 20,000/min in thresholds.json (the org allows 30,000), and the run refuses to make a call that would push the estimated spend past the 2.00 USD cap, marking the metric unscored instead, which then trips scored != attempted and exits 1. Token counts are labelled estimates because a metric's internal calls are not exposed. Library logs that can carry the OpenAI org id are silenced and a scrubbing filter redacts anything shaped like a key, an org id, or a bearer token from every log line.
